# Zabbix MegaRAID Monitoring for Windows

Zabbix 7.0 template for monitoring Broadcom / LSI MegaRAID controllers on Windows systems using StorCLI64.

The template supports multiple MegaRAID controllers in a single Windows host and automatically discovers:

- MegaRAID controllers
- Virtual Drives
- Physical Drives

Monitoring is based on a single active Zabbix agent master item. The StorCLI JSON output is collected once and processed by Zabbix using dependent items and Low-Level Discovery (LLD).

## Requirements

- Zabbix Server 7.0
- Zabbix Agent or Zabbix Agent 2 on Windows
- Broadcom StorCLI64
- StorCLI64 must be able to access the installed MegaRAID controller(s)

The template was developed and tested using:

- Zabbix 7.0
- StorCLI64 version 7.23
- Windows Server
- Multiple MegaRAID controllers in the same host

## How it works

The template uses the following data flow:

StorCLI64
    |
    v
Zabbix Agent (active)
    |
    v
megaraid.get
"MegaRAID: StorCLI raw JSON"
    |
    v
megaraid.normalized
"MegaRAID: Normalized data"
    |
    +-- Controller Discovery
    |
    +-- Virtual Drive Discovery
    |
    +-- Physical Drive Discovery


StorCLI is executed only by the master item.

The JSON returned by StorCLI is then normalized using JavaScript preprocessing. The normalized JSON contains three main arrays:

- `controllers`
- `virtual_drives`
- `physical_drives`

These arrays are used by the corresponding dependent discovery rules.

This design avoids executing StorCLI separately for every controller, Virtual Drive or Physical Drive.

## Zabbix Master Item

The central master item is:

megaraid.get


Item name:

MegaRAID: StorCLI raw JSON


Type:

Zabbix agent (active)


Update interval:

5 minutes


The item must return the JSON output generated by StorCLI64.

All controller, Virtual Drive and Physical Drive discovery is derived from this data.

The template also contains the dependent item:

megaraid.normalized


This item converts the original StorCLI JSON into a simplified internal JSON structure used by the discovery rules.

## Zabbix Agent Configuration

A UserParameter must be configured on the Windows host.

Example:

UserParameter=megaraid.get,"C:\Program Files\StorCLI\storcli64.exe" /call show all J


Adjust the StorCLI path if necessary.

After adding or modifying the UserParameter, restart the Zabbix Agent service.

The command can also be tested manually from a command prompt:

cmd
"C:\Program Files\StorCLI\storcli64.exe" /call show all J


The command must return valid JSON data for all installed MegaRAID controllers.

## Controller Discovery

Discovery key:

megaraid.controller.discovery


The controller discovery automatically creates items for every detected MegaRAID controller.

### Controller Items

The following information is monitored:

- Controller model
- Controller status
- Controller status text
- ROC temperature
- BIOS version
- Driver name
- Driver version
- Firmware version
- Firmware package build

Example item:

MegaRAID Controller 0


contains the controller model.

Firmware and driver information is extracted directly from the original StorCLI JSON, while controller status, model and temperature are read from the normalized data.

## Virtual Drive Discovery

Discovery key:

megaraid.vd.discovery


Each Virtual Drive is identified by:

- Controller ID
- Drive Group
- Virtual Drive ID

For example:

Controller 0
Drive Group 1
Virtual Drive 0


is represented as:

C0 DG1/VD0


### Virtual Drive Items

The following information is monitored:

- RAID health
- RAID state
- Access state
- Consistency
- Cache policy

### RAID Health Values

The StorCLI Virtual Drive state is converted into a numeric health value:

| Value | State |
|------:|-------|
| 0 | Optimal |
| 1 | Degraded |
| 2 | Partially degraded |
| 3 | Offline |
| 4 | Unknown |

The template contains a Zabbix value map named:

MegaRAID Virtual Drive States


## Physical Drive Discovery

Discovery key:

megaraid.pd.discovery


Physical Drives are identified by:

- Controller ID
- Enclosure ID
- Slot

For example:

C0 E252 S3


represents:

- Controller 0
- Enclosure 252
- Slot 3

### Physical Drive Items

The following information is monitored:

- Model
- Interface
- Size
- Drive Group
- Drive state
- Drive health

StorCLI states are translated into internal health values which are used by the trigger prototypes.

## Triggers

The template automatically creates triggers for important RAID conditions.

### StorCLI Availability

A trigger is generated if no StorCLI data has been received for 15 minutes:

MegaRAID: No StorCLI data for 15 minutes


Severity:

Average


### Controller Status

A trigger is generated if the controller health value is not `0`:

MegaRAID C{#CTRL}: Controller is critical


Severity:

High


### Virtual Drive Status

The following conditions are monitored:

**Degraded / Partially degraded**

MegaRAID C{#CTRL} DG{#DG}/VD{#VD}: RAID is degraded


Severity: `High`

**Offline**

MegaRAID C{#CTRL} DG{#DG}/VD{#VD}: RAID is offline


Severity: `Disaster`

**Unknown**

MegaRAID C{#CTRL} DG{#DG}/VD{#VD}: RAID status is unknown


Severity: `Average`

### Physical Drive Status

The following conditions are monitored:

**Failed**

MegaRAID C{#CTRL} E{#EID} S{#SLOT}: Physical drive failed


Severity: `High`

**Unknown**

MegaRAID C{#CTRL} E{#EID} S{#SLOT}: Physical drive state is unknown


Severity: `Average`

All triggers included in the template allow manual closing.

## Database Optimization

Many status and informational items use the Zabbix preprocessing option:

Discard unchanged with heartbeat


This reduces unnecessary history entries for values that rarely change.

Different heartbeat intervals are used depending on the type of information.

Typical examples:

- Health values: 1 hour
- Status text: 6 hours
- Hardware and firmware information: 1 day

The raw and normalized JSON master items use a history retention period of one day.

## Installation

### 1. Install StorCLI64

Install Broadcom StorCLI64 on the Windows system.

Verify that the controller is accessible:

cmd
storcli64.exe /call show all

Then verify JSON output:

cmd
storcli64.exe /call show all J


### 2. Configure the Zabbix Agent

Add the `megaraid.get` UserParameter to the Zabbix Agent configuration.

Example:
UserParameter=megaraid.get,"C:\Program Files\StorCLI\storcli64.exe" /call show all J


Restart the Zabbix Agent service.

### 3. Test the Zabbix Key

Make sure that the following key returns the StorCLI JSON:
megaraid.get


### 4. Import the Template

Import:
zabbix_template_megaraid_windows.yaml
into Zabbix.

Navigate to:
Data collection -> Templates -> Import


### 5. Link the Template

Link the template:
MegaRAID controllers by Zabbix agent
to the Windows host.

Because the master item is configured as an active Zabbix Agent item, the host must be correctly configured for active checks.

## Template Structure

The template follows this hierarchy:

MegaRAID: StorCLI raw JSON
|
+-- MegaRAID: Normalized data
    |
    +-- Controller Discovery
    |   |
    |   +-- Model
    |   +-- Status
    |   +-- Status text
    |   +-- ROC temperature
    |
    +-- Virtual Drive Discovery
    |   |
    |   +-- RAID health
    |   +-- RAID state
    |   +-- Access
    |   +-- Consistency
    |   +-- Cache policy
    |
    +-- Physical Drive Discovery
        |
        +-- Model
        +-- Interface
        +-- Size
        +-- Drive Group
        +-- State
        +-- Health


Controller firmware and driver information is also discovered per controller, but is extracted directly from the original StorCLI JSON master item.

## Multiple Controllers

The template is designed to support more than one MegaRAID controller in the same Windows host.

Each controller is identified using the Controller ID returned by StorCLI.

For example:

Controller 0
Controller 1


Virtual Drives and Physical Drives additionally contain the controller ID in their discovery data, preventing collisions between devices connected to different controllers.

## Tested StorCLI Version

Development and testing was performed with:
StorCLI64 7.23
Other StorCLI versions may work as well, provided their JSON structure and field names are compatible.
Different StorCLI versions or controller generations may return different fields or state values.

## Notes

The template relies on the JSON field names returned by StorCLI.

If Broadcom changes the JSON structure in future StorCLI releases, the JavaScript preprocessing or JSONPath expressions may have to be adjusted.

The template currently focuses on:

- Controller health
- RAID / Virtual Drive health
- Physical Drive health
- Controller temperature
- Controller firmware information
- Driver information
- Basic physical drive information
